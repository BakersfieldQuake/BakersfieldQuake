Why it was slow

About 7 s of every load was the same on every map. For each of about 1,900 textures the engine asked the disk for some 40 optional files (_norm, _glow, _gloss … as .tga/.png/.jpg/.pcx) in every loose folder. Almost none exist. It is the number of files that costs, not their size: shrinking the gun frames to 8×8 pixels saved almost nothing.

  • Engine file-lookup cache (fs_dircache): remembers which folders exist and skips the lookups. Main gain.
  • Precache gating: the tank, LAN props, Eric cannon, random NPCs and sky pads load only on maps that place them.
  • Vehicles per kind: a map with one car no longer loads all 57 vehicle models.
  • macOS app: its separate user folder doubled the lookups. soi6 13.0 → 7.9 s (−39%) once the engine fork merges the patch.

Measured and rejected: packing the gun frames into atlases saves 0.45 s for a 92 MB download.

What the profiler found

  • Visibility rays (terminal21: 71% of the frame). The engine checks whether each model and light is hidden by tracing rays that test wall faces one by one, and these maps keep thousands of faces on one tree node. The old cheap test is exact on 8 maps, so the game now picks it per map. It stays off where see-through gratings sit on solid walls (downtown: 1,979 such faces), because there it could hide a player.
  • Model lighting (downtown: 35%). Every frame, every model looked up its floor light by scanning up to 9,500 faces. Furniture and pickups never move, so the engine now caches the answer: 0.454 → 0.005 ms per frame. Checked against the uncached result a million times per map, no difference.
  • Controller polling (11%). The engine asked Windows about four empty controller slots every frame. Now once a second.

Settings tested and left alone

Coronas, decals, particle collisions and quality, and dynamic-light shadows changed nothing on terminal21 (46–47 fps each). Turning the visibility rays off completely costs morrorock 16%, so they stay on. Dynamic lights off (the menu's Simple Mode) gave 71 fps where the per-map setting gives 311.

The fps figures are from an RTX 4070 Ti, so they show relative gains. A PC with integrated graphics will be far lower in absolute terms.

Where it went

  • Shadow atlas 8192 → 4096: the engine default was one 256 MB texture for rocket and muzzle-flash shadows. Now 64 MB, same look.
  • Precache gating and vehicles per kind: 230–370 MB of video memory per map.
  • Three gun models without mipmaps (zz_gunnomip.pk3, 56 KB): 68 MB less.
  • Map-change leaks fixed in the engine: the old engine gained about 70 MB on every map change and never gave it back. Engine memory after four maps: 757 → 617 MB.
  • Low-memory mode (lowmem.cfg, model textures at half size): starts by itself under 10 GB of RAM or under 3 GB of video memory. Downtown: 2,155 → 945 MB of textures, 3.8 → 2.4 GB committed.
Server

Server script work cut by more than half

Server script statements in 75 s, soi6, 15 bots (millions)

Gib physics ("Gyro") Everything else
Table view
  • Gib physics off (gyroset 0): every gib ran about 8 script calls each server frame for 30–40 s, and one rocket into a Soi 6 bar makes about 150 gibs. 61% of all server script work. Gibs still fly and bounce. Host frame rate on soi6: 114 → 147 fps (+29%).
  • Gib budget for Soi 6 NPCs: four full showers per 10 s, then three gibs and a splat.
  • NPCs no longer resent every frame: they copied the viewer's view angle, so every mouse move re-sent each NPC in range. They now face the viewer's position.
  • Measured and left: the Soi 6 per-NPC hook. A dedicated server with 4 players used 17.7% of a core with it and 16.0% without, inside the noise, and was asleep 98% of the time.
  • Ten minutes with 15 bots on downtown: 6 million statements a second, a few percent of one core.

Method

How it was measured

  • Load time: loadtime.py runs a scratch copy of the release package in the release layout, times the map command to "entered the game", and records memory and errors. Reset settings before every run.
  • Profiling: sampler.py samples the engine's main thread every 1–3 ms. With a symbol map from an unstripped rebuild it names the engine functions.
  • Frame rate: recorded matches played back with timedemo.py. Live bot matches swing too much: three settings looked good or bad live and were all noise.
  • Out of memory: the engine run inside a Windows job object with a commit limit.
  • Server: script profiles (prvm_profile) and CPU time of a dedicated server with real clients connected.
  • Releases: base zip compared file by file with the live manifest, a draft build, the draft's manifest compared again, the exact file set smoke-tested, then the real build. Files for the server taken from the published zip and checked against the manifest, installed only while it was empty, with a backup.
  • Limits: one fast PC. Several sessions were testing on it at the same time; load repeats differ by up to 0.5 s.
  • Full detail: docs/audit-2026-11-18-performance.md and docs/engine-perf-patches-2026-11-18.md in the repository.
